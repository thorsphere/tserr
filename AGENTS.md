# Engineering & AI Collaboration Guidelines

This repository is developed using AI-assisted engineering with strict human oversight. A high bar for stability, extensive test coverage, and code hardening is maintained.

---

## 🎯 Architecture & Intent
- **Context:** Foundational two-package Go monorepo. The root package is a
  zero-dependency library providing structured, HTTP-status-aligned JSON error messages.
  The generator package (`gen`) is a library (`tserr/gen`) that reads `tserr.json` and header/footer templates to generate `tserr_messages.go`, `tserr_api.go`, and `tserr_api_test.go` using `lpcode`, `lpstats`, and `tsfio`.
- **Evolution:** Packages in this organization typically end up as a Google
  Cloud Run microservice, sometimes accompanied by a CLI helper that calls
  the service over its API.
- **Frameworks:** Pure Go standard library and thorsphere packages (keep dependencies to an absolute minimum).
- **Configuration:** `tserr` requires no runtime configuration, and `tserr/gen` is driven by a JSON configuration file (`tserr.json`).

## 🤖 AI Agent Instructions
When generating code, refactoring, or planning tasks, you MUST adhere to these technical constraints:

### 1. Components

**a) Core Library** (`/`, `package tserr`): Zero external dependencies. Must stay component-agnostic: no HTTP server wiring, no `main` imports. Hand-written core files (`tserr.go`, `tserr_nil.go`, `tserr_test.go`) plus generated files (`tserr_messages.go`, `tserr_api.go`, `tserr_api_test.go`).

**b) Code Generator** (`gen`, `package gen`): Reads tserr.json and `.header`/`.footer` template files to generate the root package's error definitions, constructors, and unit tests.

### 2. Quality & Hardening Standards
- **Testing:** Every new feature or package function requires table-driven Unit Tests. Target >85% coverage. Tests in the root package (`tserr_api_test.go`) are auto-generated per-function (`Test<Name>`, `Test<Name>Nil`) by `gen.Generate`, whereas hand-written validation tests in `gen_test.go` use table/slice-driven tests.
- **Error Handling:** Package gen uses tserr constructors (`tserr.NilPtr()`, `tserr.Op()`, `tserr.EqualInt()`, etc.), while the root tserr package is tserr itself and constructs errors via the internal `errorf(&errmsg...)` helper.
- **Code Formatting:** Use `gofmt` to format Go code.
- **Logging:** strictly return error values to callers.

### 3. Coding Style (match the existing codebase exactly)
- Never manually edit generated files (`tserr_messages.go`, `tserr_api.go`, `tserr_api_test.go`). Any new error definition or change must be made in `tserr.json` and regenerated by running `go test .` (which invokes `gen.Generate("tserr.json")` in `TestGenerate`).
- **File header:** Every `.go` file starts with the thorsphere copyright
  notice (FSL-1.1-ALv2, see any existing file) followed by the package clause.
- **Imports:** Precede the import block with `// Import packages` and annotate
  every import inline, e.g. `"strings" // Import the strings package for string manipulation.`
- **Comments:** Doc comment on every declaration — functions (exported
  and unexported), types, and package-level vars/consts. Narrate defensive
  steps inline: `// If the user cancels, return an error.`,
  `// Return no error to indicate success.`
- **Atomic lines:** Comment every code line that carries behavior of its
  own (a call, assignment, branch, or return). Scaffolding lines (braces,
  bare closures) may go without; const-block members each carry their own
  trailing comment.
- **Structs:** Doc comment above every struct declaration, and a purpose
  comment appended to every field line, e.g.
  `Model string // The model identifier for the request.`
- **Consts, vars, and types:** Doc comments open with a complete sentence
  naming the symbol. A type's doc comment states what each instance
  represents or provides; document the zero value's meaning when it is
  not obvious. Grouped consts or vars carry one doc comment for the
  group plus a short end-of-line comment per member; ungrouped
  declarations carry a full doc comment. Typed constants may lean on the
  type's doc comment instead of a group comment. Vars follow the const
  conventions.
- **Function doc comments:** Begin with the function name and state the
  contract, not the implementation: what the function returns, or — for
  functions called for side effects — what it does. Refer to named
  parameters and results directly by name, without backquotes. Name
  results in the signature only when the comment must distinguish
  multiple results; otherwise omit them. Use idiomatic openers:
  "returns" for value-plus-error functions, "reports whether" for
  booleans. A comment that merely restates the function name or narrates
  implementation steps does not satisfy this rule — narration belongs on
  the atomic lines inside the body.
- **Errors:** Check every returned error. Never panic. Wrap with the
  appropriate `tserr` constructor.
- **Tests:** gen uses external test package `gen_test` (`gen_test.go`) and bridges unexported symbols via `export_test.go`.
  The root package uses internal test package `package tserr` (`tserr_test.go` and generated `tserr_api_test.go`) so tests can directly access unexported `errorf`, `errmsg`, `errwrap`, and `errmsg<Name>` vars.
  `TestGenerate` in `gen_test.go` reads `tserr.json` and writes the generated .go files to `..` on disk via `tsfio` / `lpcode`.
  Unit tests must NOT depend on external
  binaries or remote services — tests must pass in any environment (CI,
  Cloud Build).

### 4. Commands
- Build: `go build ./...` — Test: `go test ./...` — Vet: `go vet ./...`
- Format check: `gofmt -l .` (must output nothing)
- Toolchain: latest Go toolchain (per `go.mod`)

### 5. Commit Messages
- Commits in this repository follow strict Conventional Commits:
  `<type>(<scope>)[!]: <imperative description>` with a header ≤72 bytes,
  a body wrapped at 72 explaining WHAT and WHY, and a
  `BREAKING CHANGE:` footer when consumers must adapt.
- **Scope is mandatory:** Every commit header MUST include a parenthesized
  scope — never omit `(<scope>)`.
- When a format or contract is defined in multiple coupled places, a change MUST be
  applied to all of them in the same commit — never one side alone.

### 6. Deliberate Design Decisions — do NOT "fix" these
- **Error ID 0 and NilPtr separation**: `NilPtr()` is intentionally isolated in `tserr_nil.go` with hardcoded ID 0, and `errorf(nil)` formats `nilPtr` directly via `fmt.Errorf` instead of calling `NilPtr()` to avoid infinite recursion.
- **Skipped Error ID 13**: In `gen.go` (`genMessages`), error ID 13 is deliberately skipped (`if i++; i >= 13 { i++ }`). Do not "fix" the off-by-one jump from ID 12 to ID 14.
- **Positional Error IDs**: Error IDs are assigned sequentially from their order in `tserr.json`. New errors should be appended to the end of `tserr.json` to avoid shifting existing IDs unnecessarily.
- **Calling conventions (1-arg vs multi-arg)**: Single-parameter errors take a direct value parameter (`func Foo(x string) error`), while multi-parameter errors take a pointer to an <ErrorName>Args struct (`func Bar(a *BarArgs) error`) and return `NilPtr()` if `a == nil`.
- **Running `go test .` regenerates code**: `TestGenerate` in `gen_test.go` executes `gen.Generate("tserr.json")`, which overwrites `tserr_messages.go`, `tserr_api.go`, and `tserr_api_test.go` in the root directory.
- **%w inside JSON error format**: errformat in `tserr.go` intentionally uses "%w" inside `fmt.Errorf(errformat, e.Id, e.C, fmt.Errorf(e.M, a...))` so inner errors remain wrapped and inspectable via `errors.Unwrap` / `errors.Is` / `errors.As`.
